Agent threads: architecture

A proof of concept for cloud coding agents. One Mastra agent, dev, where every thread is an agent. Agents start other agents with tools, talk to each other with signals, and run commands in per-user Modal sandboxes whose files live on a durable Modal volume. Several users share one server without seeing each other's threads, sandboxes, or files. A web app shows each user their agent tree, conversations and sandbox files.

Threads as agents

There is no subagent registry. A child is a new thread of the same dev agent whose metadata names its parent and its sandbox. Children are real threads: you can open them in Studio, read them, and message them.

Mount

volume.withMountOptions({ subPath: sandboxId }) at /mnt/work. A sandbox can only see its own folder. No bucket, no credentials in the VM.

One view of the files

ModalFilesystem({ basePath: '/mnt/work' }) means the file tools and execute_command read and write the same files. Commands start in /root, so the agent is told to use cwd "/mnt/work".

Local mode no Modal token

Each sandbox is a folder .sandboxes/<user-hash>/<sandboxId> with LocalFilesystem + LocalSandbox.

Workspace cache

An agent resolves its workspace several times per run, so workspaces are cached per user + sandbox (up to 500, oldest dropped). A dropped one reconnects by id.

start_agent flow

  1. User asks the parent thread to split work. Request is signed in; server sets resourceId.
  2. Parent calls start_agent({ task, sandbox: "new", idempotencyKey }).
  3. Tool checks depth ≤ 2, children ≤ 5 per thread, running ≤ 10 per user, extra sandboxes ≤ 5 per user; derives ids from the key if given.
  4. Tool creates thread agent-<id> with metadata { sandboxId: "sb-<id>", parentThreadId, depth }.
  5. Tool sends the task with sendMessage(…, { ifIdle: { streamOptions: { requestContext } } }); the context carries user, sandbox, parent.
  6. Child run resolves its workspace → ownership check → Modal VM starts with folder sb-<id>/ mounted; toolkit CLIs (gh) installed.
  7. Child works, then calls report_to_parent: the report is saved on its thread, then sent as an agent-report notification signal.
  8. Parent wakes (or receives it mid-run) and continues with the report. If the signal never arrives, wait_agent reads the saved report.

Several users

Identity tested

  • Resource id comes only from sign-in (reserved key).
  • Server returns 403 for another user's thread.

Sandboxes tested on Modal

  • Sandbox identity is <user-hash>-<sandboxId>; two users' main never meet.
  • A client-supplied sandboxId is trusted only if one of the user's threads already uses it.
  • Anonymous runs get no workspace.

Tools tested

  • message / read only reach the same user's threads.
  • interrupt only reaches the caller's own children.

Shared credential gap

  • Every sandbox gets the same GH_TOKEN. Use a read-only token, or per-user tokens before production.

Web app

A Vite + React 19 app in web/ (Tailwind v4, shadcn/ui and AI Elements components, Streamdown for markdown). It talks to the same server: chat through @mastra/react's useChat with thread signals, history through the memory route, everything else through the app routes below. In development, Vite proxies /api and /app to the server.

Screens

  • Agents: tasks with their agents nested; status dots; sandboxes and limits.
  • Conversation: messages, foldable commands, links to started agents, report cards, a message box that reaches the agent mid-task.
  • Files: the sandbox's /mnt/work, read-only.

Actions

  • New task in main, a new sandbox, or an existing one.
  • Stop the current run; Close / Reopen a task; Delete a task, its agents and unused sandbox files.
  • Resume / Dismiss an interrupted agent.

Restarts & attention

Runs live in the server's memory. src/mastra/runs.ts polls the agent's active runs every 2 s and writes to each thread's metadata: run: { boot, startedAt } while one is going, and finishedAt plus run: null when it ends.

Interrupted tested

A run recorded by an earlier server process never finished, so the thread shows interrupted: an amber dot, a banner, and tool calls marked "Didn't finish". Resume sends a message asking the agent to check its files and continue; Dismiss clears the state. Nothing resumes on its own.

To look at tested

A task is flagged (blue dot, bold title, count in the header and tab) when it's top-level, not closed, nothing in it is running, and finishedAt is after seenAt. Opening any thread in the task marks it seen, including one that finishes while it's open.

Known gaps

Deleting outside the app gap

Only the app's Delete empties a sandbox's folder. Threads deleted from Studio or the API leave it behind, unreachable and no longer counted toward the limit.

Idle VMs keep running gap

A VM runs for its full hour even when idle, and a command running when it ends is cut off.

One server process gap

Signals and the running-agent count are in-process. Multiple instances need shared PubSub (Redis / Valkey streams).

Restarts gap

A restart stops every running agent; they're shown as interrupted but don't resume on their own. With observational memory, steps from the cut-off run can go unsaved (in one test, 3 of 6 commands), so a resumed agent may redo work. Runs shorter than the 2 s poll aren't recorded.

Studio gap

A message sent to a child from Studio doesn't carry its sandbox id, so it runs in main.
